# 项目说明 · 架构与技术决策

---

## 1. 问题定义

工程档案归档要求提交两本 Excel：《文件台账》（74 列，一行一件）与《案卷台账》（60 列，一行一卷）。

难点不在数据量，在**规则**：

- 130 多个字段里，实际必填约 30 个，其余靠推导或固定值——人容易填错列
- 规则隐含在规范里（"分类号须单本一致""年度取文件日期前四位""四个日期依次顺延"），没人会逐条核
- 两本台账之间有依赖（归档日期须相同、案卷年度取卷内最晚）
- 错了要退回重做，影响验收节点

**目标**：把规范变成可执行的检查，以及让"只填必要信息就能生成合规台账"成为可能。

```

        │ 浏览器                                     │
        │                                          │
        │  index.html                              │
        │  ├─ app.js          界面控制、状态、渲染    │
        │  ├─ engine/engine.js 规则引擎（纯函数）     │
        │  ├─ engine/excelio.js Excel ↔ 数据模型     │

        │  └─ vendor/exceljs   本地内置，不走 CDN     │
        └──────────────────────────────────────────┘
                        ▲ 静态文件
        ┌───────────────┴──────────────┐
        │  server/server.js             │
        │  零依赖 · 127.0.0.1 · 只读静态  │
        └───────────────────────────────┘
```

### 分层职责

| 层 | 职责 | 不做什么 |
| --- | --- | --- |
| `engine.js` | 规则判定与数据推导 | 不碰 Excel，不碰 DOM |
| `excelio.js` | 格式转换与样式写入 | 不含业务规则 |
| `app.js` | 状态与交互 | 不做计算 |
| `data.js` | 基准数据与模板 | 不含逻辑 |
| `server.js` | 静态分发 | 不接收文件、不落盘 |

## 3. 关键决策记录

### 3.1 纯前端，不做后端

**约束**：数据敏感（全宗号/单位名称/人员）、网络受限（内网）、单机单用户、数据量小。

**决策**：所有计算在浏览器内完成，本地服务只分发静态文件。

**代价**：PDF 页数只能估算（浏览器端正则匹配）；无法做多用户协作；无法服务端留痕。

**如果需求变化**：出现"多人共用 + 审计留痕"，必须上服务端。这个架构不预留扩展，是刻意的——为当前场景优化。

### 3.2 ExcelJS 而非 SheetJS

SheetJS 社区版**不支持写样式**（`cell.s` 在写入时被忽略），无法满足"宋体 11 号居中"的硬要求。

ExcelJS 支持 `cell.font` / `cell.alignment` / `cell.numFmt`，且浏览器与 Node 共用同一份代码。

**代价**：包体积 880KB → 950KB。

### 3.3 不用构建工具

**原因**：必须支持 `file://` 双击打开，而打包产物是 ES Module，在 `file://` 下被 CORS 拦截。

**做法**：手写 IIFE + UMD 封装，浏览器与 Node 都能直接加载。

### 3.4 数据内联到 JS

`file://` 下 `fetch()` 本地 JSON 会被拦截。所以把基准、分类映射、两个 Excel 模板全部转 base64 塞进 `data.js`（约 42KB）。

**顺带收益**：整个目录可任意搬移，不依赖相对路径。

## 4. 数据模型

引擎不认识 Excel，只认识：

```js
sheet = {
  label: '文件台账',
  header: ['项目代号', '项目排序号', ...],
  index:  { '项目代号': 0, '项目排序号': 1, ... },
  rows: [
    { __row: 2, '项目代号': '0011', '文件档号': 'D0109-...-001', ... },
    ...
  ]
}
```

设计要点：

- **行是对象不是数组**：列顺序变化不影响逻辑
- **`__row` 保留 Excel 行号**：报告要能定位到具体行
- **空值统一用 `null`**：区分"没填"和"填了空字符串"

## 5. 规则组织

```
RULE_CATALOG = [
  ['F1', '文件台账', '固定值列一致性', 'ERROR', '说明文字…'],
  ...
]
```

报告按目录顺序渲染，所以：

- 加规则 = 改数组 + 加检查逻辑
- 调级别 = 改数组里的字符串
- 改说明 = 改数组

**通用检查抽出来**：`checkUniformColumn(colName, ruleId, baseValue, kind)` 一个函数覆盖 F1/F2/J1/J2 共 24 个列。

## 6. 核心算法

### 6.1 日期倒推链

以归档日为锚，逐级取前一个工作日：

```
归档 = 锚点
检查 = prevWorkday(归档)
立卷 = prevWorkday(检查)
编制 = prevWorkday(立卷)
```

`prevWorkday` 每次减一天，遇到周六/周日继续减。

**为什么倒推**：归档日期是确定的（就是今天），其余三个是推出来的。正推会引入"从哪天开始"的额外自由度。

### 6.2 档号拆解

```js
/^(.+)-(\d{3})$/
```

贪婪匹配最后一个三位数字段。`D0109-KJG01-0011-800-001` → 卷号 `D0109-KJG01-0011-800`、序号 `1`。

**上限**：卷内超过 999 件不匹配。实际不会出现。

### 6.3 可疑案卷：四维启发式

| 维度 | 判据 | 阈值来源 |
| --- | --- | --- |
| 件数离群 | 同类中位数 ≥4 且本卷 < 中位数×60% | 真实数据试出来的 |
| 单据类型离群 | 卷内 ≥5 件时某类型 ≤2 件且占比 ≤25% | 同上 |
| 子阵覆盖不全 | 同类普遍覆盖 N 个，本卷更少 | 业务经验 |
| 页数-脊背不匹配 | 每毫米承载页数低于同类最优 3 倍 | 真实数据试出来的 |

**第 4 维的实现要点**：不做两两比较（O(n²) 且对称重复报），而是先算密度取最大值，只报密度最低者。

### 6.4 生成器的空值推导

| 字段 | 来源 |
| --- | --- |
| 全宗号/KJG码/项目代号/分类号/案卷号 | 拆档号 |
| 所属卷号 | = 案卷档号 |
| 卷内序号/文件档号 | 按出现顺序递增 |
| 年度 | 日期前四位 / 案卷取卷内最晚 |
| 文字页数 | 页数 − 图纸页数 |
| 分类名称/保管期限/代码 | 查 `category_map` |
| 17 个固定值列 | 查 `baseline` |

任一项无法推导 → 收集全部错误一次性报出并中止，**不产半成品**。

## 7. 验证策略

| 层次 | 方法 | 目的 |
| --- | --- | --- |
| 闭环 | 生成 → 回检，要求 0 错误 | 固化两套逻辑的口径契约 |
| 保真 | 真台账提取要素 → 重新生成 → 逐字段比对 | 证明不是"造了个格式对但内容错的东西" |
| 反例 | 注入已知错误，看能否检出 | 证明规则不是空壳 |
| 变异 | 改一处数据，只应报对应的一条 | 证明规则之间不互相污染 |

实际往返验证结果：26 件 × 25 字段，原值非空部分 **0 处差异**。

## 8. 已知局限

| 局限 | 影响 | 后续 |
| --- | --- | --- |
| PDF 页数为估算 | 压缩对象流的 PDF 可能不准 | 引入 pdf.js 或 WASM |
| 只读第一个 sheet | 多 sheet 文件只处理首个 | 加选择器 |
| 节假日未跳过 | 日期可能落在春节等 | 引入年度节假日表 |
| 分类映射需手工维护 | 新分类号会中止 | 从历史台账学习 |
| 无性能实测 | 5000 行未验证 | 补压测脚本 |
| 阈值是启发式 | 可疑卷可能误报 | 积累数据后调参 |
