# 项目复盘与面试准备 · 档案台账工作台

> 用途：面试前过一遍，能讲清楚「这是什么、怎么做的、难点在哪、为什么这么选」。

---

## 一、30 秒版本（电梯陈述）

> 我做过一个工程档案归档的台账工具。业务上，每个项目验收要交两本 Excel——《文件台账》和《案卷台账》，加起来 130 多个字段，规则之间有联动，人工核对一本 70 件的台账要两三个小时，还经常漏。
>
> 我把归档规范拆成 25 条可执行规则，做成一个**纯本地运行的浏览器工具**：检查两本台账并给出带行号的问题报告，也能反过来只填 8 项要素就自动生成两本合规台账。
>
> 技术上关键决定是**不要后端**——所有 Excel 读写和规则计算都在浏览器里跑，文件不出本机。因为台账里有全宗号、单位名称、人员姓名，这类数据不适合上传。代价是 PDF 页数只能估算。
>
> 目前的验证方式是闭环：生成器的输出必须能通过检查器零错误，我把这个跑成了自动化测试，38 项断言。

## 二、简历怎么写

**一行版**

> 独立设计并实现档案台账工具（JS，纯前端 + 零依赖本地服务），将 25 条归档规范固化为可执行规则，实现台账自动检查与生成的双向闭环，人工核对耗时从小时级降至秒级。

**三点版**

- **规则引擎**：把散落在规范文档里的归档要求拆成 25 条可独立演进、带严重级别的规则，检查器与生成器共用同一套口径，互为逆过程的闭环自测
- **离线优先架构**：纯浏览器计算，零后端、零依赖、断网可用；Excel 模板、固定值基准全部内联，规避 `file://` 下的资源加载限制
- **工程化**：38 项自动化断言覆盖日期倒推、缺陷注入、生成闭环；引入档号化的版本管理，为内网环境设计多源更新与离线更新包方案

## 三、项目背景（面试官一定会问「为什么做这个」）

### 3.1 业务场景

光伏电站工程档案验收，施工单位要把纸质资料电子化后归档进档案系统。归档前必须准备两本导入台账：

- **《文件台账》**：74 列，一行一件文件。核心是档号体系——`全宗号-KJG码-项目代号-分类号-案卷号-卷内序号`
- **《案卷台账》**：60 列，一行一个案卷（若干相关文件打成一卷）

### 3.2 痛在哪

| 痛点 | 具体表现 |
| --- | --- |
| 字段太多 | 实际必填的约 30 个，其余靠推导或固定值，但人工容易填错列 |
| 规则隐式 | "分类号必须单本一致""年度取文件日期前四位""四个日期要依次顺延"——这些规则写在规范里，没人会逐条核 |
| 跨表联动 | 两本台账的归档日期必须相同；案卷年度要取卷内最晚的那一年 |
| 错误代价高 | 台账导入档案系统后才发现错，要退回重做，影响验收节点 |
| 人工耗时 | 一本 70 件的台账，逐条核对 + 手动排版，2–3 小时 |

### 3.3 谁提的需求

是我自己在实际归档工作中反复做这件事，先把规则写成了 Python 脚本自用，跑通后发现两个问题：一是同事不会用命令行，二是规则口径在真实数据上反复被推翻。所以决定做成任何人都能双击打开的网页工具。

> **面试话术**：这不是一个"老板派下来的需求"，是我从自己的工作痛点里抽象出来的。好处是我同时是需求方和开发者，规则口径能当场对齐；坏处是我一开始严重低估了"规则本身会变"这件事。

## 四、架构与技术选型

### 4.1 整体结构

```
┌─────────────────────────────────────────────┐
│  浏览器                                      │
│  ┌──────────┐   ┌──────────────┐            │
│  │ app.js   │──▶│ engine.js    │  纯函数     │
│  │ 界面控制  │◀──│ 规则引擎      │  无副作用   │
│  └────┬─────┘   └──────────────┘            │
│       │                                     │
│  ┌────▼─────┐                               │
│  │excelio.js│  ExcelJS 读写 + 样式         │
│  └────┬─────┘                               │
│       │                                     │
│  ┌────▼─────┐  ┌──────────────┐            │
│  │ 用户文件  │  │ data.js      │ 基准+模板   │
│  └──────────┘  └──────────────┘            │
└─────────────────────────────────────────────┘
              ▲ 只分发静态文件
        ┌─────┴──────┐
        │ server.js  │  零依赖，127.0.0.1
        └────────────┘
```

### 4.2 三个关键选型

**① 为什么不做后端**

第一反应都是"传上来我帮你算"。但这个场景下：
- 数据敏感（全宗号、单位名称、人名）
- 用户网络受限（内网、涉密环境）
- 单次数据量小（典型 70 行 × 74 列，最大见过 5000 行）
- 无并发需求（一个人用）

纯前端同时解决了安全、离线、部署三个问题。**这是产品约束倒推的技术决策，不是因为前端简单**。

**② 为什么是 ExcelJS 而不是 SheetJS**

我先用了 SheetJS（xlsx），跑通了读写，然后发现一个硬伤：**免费版不支持写样式**。而需求里明确要求输出"宋体 11 号、水平垂直居中、文本格式、自动换行"。

ExcelJS 的 `cell.font` / `cell.alignment` / `cell.numFmt` 都能直接写，而且浏览器和 Node 共用同一份代码。换库代价是包体积从 880KB 涨到 950KB，可以接受。

**③ 为什么不用构建工具**

没用 webpack/vite/babel。理由：
- 目标环境是内网 Windows，不能指望有 Node 环境
- 必须支持 `file://` 直接双击打开，模块化打包产出的是 ES Module，`file://` 下会被 CORS 挡住
- 代码量小（约 2000 行），手写 IIFE + UMD 完全可控

代价是没有 tree-shaking、没有 HMR，改一次要手动刷。**这是为了部署环境做的妥协，不是不会用工具链**。

## 五、核心设计

### 5.1 规则引擎：数据模型与 Excel 解耦

引擎不认识 Excel，只认识一个极简模型：

```js
sheet = {
  header: ['项目代号', '项目排序号', ...],   // 列名
  rows: [ { __row: 2, '文件档号': '...', ... } ]   // 一行一个对象
}
```

这样拆的好处：
- 单元测试不需要造 Excel 文件，构造对象就行
- 换 Excel 库（SheetJS → ExcelJS）只改 `excelio.js`，引擎一行不动
- 未来接 CSV / 数据库导出，只要产出一样的模型

**面试可能追问**：为什么行数据用对象而不是数组？
> 数组要靠列索引，一旦台账列顺序变了就全错。用列名做 key，列顺序无关，而且 `get(row, '文件档号')` 可读性强。代价是同名列只保留第一个，这在台账里不会出现。

### 5.2 规则的三个层级

25 条规则不是平铺的，按性质分三层：

| 层级 | 例子 | 判定方式 |
| --- | --- | --- |
| 通用列检查 | 固定值列、单本一致列 | 一个函数 `checkUniformColumn` 复用 24 次 |
| 结构性检查 | 档号构成、序号连续、四日期链 | 每类一个专用函数 |
| 跨表联动 | 归档日期一致、案卷年度 | 需要两本台账的中间结果 |

通用列检查抽出来的 `checkUniformColumn(colName, ruleId, baseValue, kind)` 覆盖了 F1、F2、J1、J2 四组规则共 24 个列，是这个引擎里复用度最高的一段。

### 5.3 「允许为空」与「每卷首行填写」

这是踩坑最深的一个点，值得单独讲（见 6.3）。

台账是档案系统导出的，字段采用**每卷首行填写、同卷其余行留空**的写法——类似合并单元格的平铺版。

如果按"每行都必须有值"去校验，一个 70 行的台账会报几百条假警报。所以规则改成：

- 某列有空格 → **不算错**
- 某列**整列全空** → 错误（说明压根没填）
- 某列所有**非空值**必须唯一

这个语义修正把假警报从 137 条降到 11 条。

### 5.4 日期倒推链（最常被追问的算法）

归档要求四个日期形成一条链：编制 → 立卷 → 检查 → 归档，每级比前一级晚，且都要落在工作日。

实现方式是**以归档日为锚，逐个工作日往前倒推**：

```js
function prevWorkday(d) {
  let cur = d - 1 天;
  while (cur 是周六或周日) cur -= 1 天;
  return cur;
}

检查 = prevWorkday(归档)
立卷 = prevWorkday(检查)
编制 = prevWorkday(立卷)
```

例：归档 2026-10-26（周一）→ 检查 10-23（周五，跳过 24/25）→ 立卷 10-22 → 编制 10-21。

**为什么是倒推而不是正推？** 因为归档日期是确定的（就是今天），其余三个是推算出来的。正推会引入"从哪天开始"的额外自由度。

**这个规则被推翻过三次**，见 6.1。

### 5.5 可疑案卷识别（信息过滤问题）

原始需求是"脊背宽度每次都要提醒检查"。但一个 40 卷的台账报 40 条提醒，等于没提醒。

所以改成一个**异常检测**问题，四个维度命中任一才报：

| 维度 | 判据 | 设计意图 |
| --- | --- | --- |
| 件数离群 | 同类卷中位数 ≥4 且本卷 < 中位数×60% | 件数骤减说明可能漏归档 |
| 单据类型离群 | 卷内 ≥5 件时，某类单据 ≤2 件且占比 ≤25% | 一堆逆变器资料里混进一张保修卡 |
| 子阵覆盖不全 | 同类普遍覆盖 N 个子阵，本卷只覆盖更少 | 别的卷有 001/002/003，这卷只有 001 |
| 页数与脊背不匹配 | 每毫米承载页数低于同类最优者 3 倍以上 | 20 页和 511 页都是 50mm 厚 |

第四类是迭代中补的——真实数据显示三卷脊背都是 50mm，但页数分别是 20 / 394 / 511，前三类都没抓到。

**面试可能追问**：阈值 60%、25%、3 倍怎么定的？
> 老实说是在真实台账上试出来的，没有统计依据。第一版用的是"件数 < 中位数一半"，在一份只有 3 卷的样本上误报了正常卷；后来放宽到 60% 并加了"中位数 ≥4 件"的下限才稳定。**这是典型的启发式规则，不是模型，我在文档里也标注了是"值得看一眼"而非"判定对错"。**

### 5.6 「页数-脊背」为什么不报两卷

第一版实现是对称的：A 比 B 少 25 倍页数但一样厚 → A 和 B 都报。结果同一条问题报两次，而且报错方向不明确。

改成看**密度**（页数 ÷ 脊背毫米数）：密度最低的那卷才是"太厚了"，只报它。511 页配 50mm 是合理的（10.2 页/mm），20 页配 50mm 才不合理（0.4 页/mm）。

## 六、难点与解决（面试重头戏）

> 面试官问"遇到什么困难"时，不要讲"遇到了 bug 然后修好了"，要讲**判断**和**权衡**。

### 6.1 难点一：规则口径本身在变（最大的坑）

**现象**：日期规则我实现过三版。

| 版本 | 口径 | 为什么被推翻 |
| --- | --- | --- |
| v1 | 编制 = 立卷 = D；检查 = D+1 工作日；归档 = 检查+1 工作日 | 是从样本数据反推出的 |
| v2 | 四个日期各晚一日，严格递增 | 业务方说"各晚一日" |
| v3（现行） | 以归档日为锚倒推工作日链 | 发现 v2 无法处理"归档写当日"的要求 |

**我的判断**：这不是需求变更，是**我一开始没有把隐性规则问清楚**。

第一个版本是我从两行样本数据里"猜"出来的规律——样本恰好是编制和立卷同一天，我就以为是规则。后来发现那只是那批资料的实际情况。

**解决方式**：
1. 规则不再硬编码在代码里，改成 `RULE_CATALOG` 数据结构（id、名称、级别、说明），报告按目录渲染
2. 每条规则的说明写进文档，改规则时同步改文档
3. 加 `--fix-dates` 参数，把"按新口径批量修正历史数据"变成一次操作而不是手工改

**反思**：需求不明确时，应该先拿**反例**去验证，而不是拿正例去归纳。"编制和立卷同一天"这个现象，当时如果问一句"这两个日期可能不相同吗"，就能一次问对。

### 6.2 难点二：Excel 样式保真

**现象**：SheetJS 写的文件打开后是默认字体、无自动换行，和要求的"宋体 11 号居中"不符。

**排查**：查文档发现 SheetJS 社区版把 style 写入归到了 Pro 版，`cell.s` 属性在写入时被忽略。

**决策**：换 ExcelJS。评估过另外两条路：
- 自己解 zip 改 `styles.xml` → 能work，但要处理 sharedStrings、cellXfs 索引，200 行代码维护成本高
- 让用户自己调格式 → 违背"一键出成品"的产品目标

换库是成本最低的正解。

**踩到的第二个坑**：换成 ExcelJS 后，数据行没被清干净——模板原有 74 行数据仍在，导致写出的文件回检报 108 个错误。

原因：`ws.spliceRows(2, ws.rowCount - 1)` 在这个文件上没有真正收缩行集合。改成"先 splice 再逐格置空"的兜底方案：

```js
try { ws.spliceRows(2, ws.rowCount - 1); } catch (e) {}
for (let r = 2; r <= maxRow; r++)
  for (let c = 1; c <= maxCol; c++)
    ws.getRow(r).getCell(c).value = null;
```

**教训**：第三方库的"删除行"语义要验证，不能只看方法名。而且**必须回读验证**——如果只检查"写出没报错"就交付，这个 bug 会直接到用户手里。

### 6.3 难点三：假警报比漏报更致命

**现象**：第一版检查器在真实台账上报了 137 个错误，其中绝大部分是"固定值列存在空值"。

**分析**：台账是"每卷首行填、其余行留空"的导出格式。我按"每行都要有值"去判，自然全红。

**这是个典型的领域知识缺失**：我拿到的是 Excel，但没意识到它背后是档案系统的平铺导出。

**解决**：改成"非空值必须唯一 + 整列全空才算错"。结果从 137 条降到 11 条，剩下的都是真问题（缺年度、缺页数）。

**连带发现**：修完假警报后，剩下 11 条里有 2 条是真问题——归档日期有两个值（`20260803` 和 `20260930`），这个错误如果混在 137 条里根本没人看。

**这条经验我印象最深**：**检查工具的价值不在于报出多少问题，而在于报出的每一条都值得看。**

### 6.4 难点四：`file://` 下读不了本地资源

**现象**：直接双击 `index.html` 时，`fetch('assets/engine/baseline.json')` 被 CORS 挡住。

**约束**：内网电脑不能装 Node，所以必须支持双击打开。

**解决**：把 JSON 和 Excel 模板全部转成 base64 内联进 `data.js`：

```js
window.LEDGER_BASELINE = {...};
window.LEDGER_TPL_FILE = "UEsDBBQ...";   // 74 列的模板 xlsx
```

代价是 `data.js` 涨到 42KB，换来零依赖可用。启动时 `atob` 还原成 ArrayBuffer 直接喂给 ExcelJS。

**顺带解决的问题**：不用管相对路径、不用管部署目录结构，整个文件夹拷到哪都能跑。

### 6.5 难点五：怎么证明"它是对的"

这类工具最怕"看起来没报错"但其实算错了。我用了三个层次：

**① 闭环测试（最强）**
生成器的输出必须能通过检查器零错误。这条如果成立，说明两套逻辑的规则口径一致。

```js
const g = buildLedgers(records);         // 生成
const result = check(g.fileSheet, g.juanSheet);  // 立刻回检
assert(result.errors === 0);
```

**② 往返验证（保真度）**
从现有真台账里提取 8 项要素，重新生成一遍，逐字段比对。

实际结果：**26 件 × 25 字段，原值非空的部分 0 处差异**。原值为空的 401 处被补全了——那是"每卷首行填写"的留空，补全后同样合规。

**③ 缺陷注入**
往正确的数据里塞错误，看能否检出：

```js
broken.rows[0]['文件页数'] = 999;                    // 应该报 F7
broken.rows[1]['文件档号'] = broken.rows[0]['文件档号'];  // 应该报 F3
broken.rows[2]['年度'] = 1999;                       // 应该报 F6
```

三种都检出，说明规则不是"永远返回通过"的空壳。

**面试话术**：
> 检查类工具最大的风险是假阴性——它说没问题，其实有。所以我不敢只用"跑通了"作为验收标准，必须有反向验证：注入已知错误看能不能抓出来。

## 七、测试策略

`test/run-tests.js`，38 项断言，纯 Node 跑，无测试框架依赖：

| 组 | 覆盖内容 |
| --- | --- |
| 1 日期倒推链 | 周五/周一/周日三种锚点，验证跨周末回退 |
| 2 题名拼装 | 补项目全称、补厂家、已带前缀不重复拼 |
| 3 真实台账检查 | 加载 samples，验 0 错误 + 可疑卷识别 |
| 4 缺陷检出 | 注入 3 处缺陷，验 6 个错误被检出 |
| 5 生成器闭环 | 生成 → 回检 0 错误，档号/年度/页数正确 |
| 6 允许项 | 日期为空不判错，且记入提示 |
| 7 案卷号流水 | 连续不报错、跳号能抓 |

**为什么不用 Jest/Vitest**：目标环境要能 `node test/run-tests.js` 直接跑，不发散依赖。自己写 20 行断言够了。

## 八、已知局限（主动说出来，比被问出来好）

| 局限 | 影响 | 如果继续做 |
| --- | --- | --- |
| PDF 页数是估算 | 浏览器端正则匹配 `/Type /Page`，遇到压缩对象流会不准 | 引入 pdf.js，或用 WASM 版 poppler |
| 只支持单工作表 | 一个 xlsx 只读第一个 sheet | 加 sheet 选择器 |
| 无可视化预览 | 只能看报告，看不到台账长什么样 | 加表格预览面板 |
| 分类映射表要手工维护 | 遇到新分类号会报错中止 | 支持从历史台账自动学习映射 |
| 没有多用户/协作 | 单人工具 | 真要多人就该上服务端了 |
| 阈值是启发式 | 可疑卷判定可能误报/漏报 | 积累数据后调，或改成可配置 |

## 九、面试 Q&A

### A. 架构与选型

**Q1：这个项目为什么不做成 Web 服务？不是更通用吗？**

> 三个约束决定了不能做：
> 1. **数据性质**——台账有全宗号、单位名称、人员姓名，属于不适合出内网的数据
> 2. **网络环境**——实际用户环境是内网，连外网 CDN 都访问不了
> 3. **使用规模**——单机单人单次，没有并发需求
>
> 做成 SaaS 会引入服务器成本、数据合规风险、运维负担，而收益是零。反过来，纯前端带来的"断网可用、零安装"，恰恰是这个场景最需要的。
>
> 如果需求变成"部门 10 个人共用一份台账并留痕"，我会立刻上服务端——因为那时候协作和审计才是核心。

**Q2：纯前端怎么保证用户数据不泄露？**

> 架构上就没有出网的路径。具体三层：
> 1. 没用任何 CDN，ExcelJS 本地内置；运行时 `fetch` 只用于"检查更新"，且用户不点就不发请求
> 2. 本地服务只做静态文件分发，没有接收文件的接口，代码里没有 `multipart` 解析
> 3. 全部计算在浏览器内存里完成，结果通过 Blob + `URL.createObjectURL` 下载，不落盘不中转
>
> 验证方式也简单：断网跑一遍，功能完整。

**Q3：为什么不用 React/Vue？**

> 页面只有三个标签页、两个上传区、一个结果列表，状态不超过 10 个字段。上框架的收益是组件复用和状态管理，而这个规模下我的 `state` 对象 + 直接 DOM 操作已经够清晰。
>
> 更关键的是构建链路——用框架就要打包，打包产物是 ES Module，`file://` 下会被 CORS 挡住，而"双击打开"是这个项目必须支持的入口。
>
> **这是场景约束下的选择，不是否定框架。**如果要做表格预览、行内编辑，我会用框架。

**Q4：130 多个字段，为什么只检查 25 条规则？剩下的不管吗？**

> 剩下的分三类：
> - **固定值**（17 个列）——已经在 F1/J1 里覆盖，靠列清单驱动，不是一条规则一个字段
> - **系统自动生成**（创建人、迁移标记等）——不由人工填，没有校验价值
> - **暂时没有业务规则**（如紧急程度）——填错也不影响归档
>
> 25 条是"会出错且出错有后果"的并集，不是字段数的比例。

### B. 技术细节

**Q5：日期为什么跳过周末，不跳过法定节假日？**

> 因为目前的规则只约束周六日。春节、国庆这些如果没有跳过，会算出"大年初一立卷"这种明显不合理的日期。
>
> 完整做法是引入节假日表（每年国务院公布），按行政区维护。我没做，因为：
> 1. 需要每年更新数据，维护成本高
> 2. 归档日期的实际误差容忍度是"几天"，不是"精确到日"
>
> 但这是个已知缺口，如果业务上真的会因为日期落在假期被驳回，就必须补。

**Q6：档号拆解如果遇到多段横线怎么办？**

> 用**贪心匹配最后一个三位数字段**：正则 `^(.+)-(\d{3})$`。前面的 `.+` 贪婪匹配，所以 `D0109-KJG01-0011-800-001` 会正确拆成卷号和序号，即使卷号里本身含横线也不会错。
>
> 但确实有个隐患：如果卷内序号超过 999，正则就不匹配了。一台机组的文件一般不会到 999 件，我在规则文档里标注了这个上限。

**Q7：大台账性能怎么样？5000 行会不会卡？**

> 没有实测过 5000 行，这是我要补的。已知的复杂度：
> - 规则里最重的是 `checkUniformColumn`，每列遍历一次，O(列数 × 行数)
> - 档号重复检测用 Map 计数，O(n)
> - 唯一一个 O(n²) 是我第一版的"页数-脊背"两两比较，后来改成先算密度取最大值，降到 O(n)
>
> 5000 行 × 74 列大概是 37 万个单元格，ExcelJS 解析是瓶颈（不是我的规则）。我估计在 2–5 秒量级，但**这是猜测，应该实测**。

> 如果面试官追问"那你为什么不测" —— 诚实回答：目前真实数据最大 72 行，没遇到性能问题，所以优先级排后了。如果被要求，我可以在 10 分钟内补一个压测脚本。

**Q8：可疑案卷的判定会不会误报？**

> 会，而且必然会。这是启发式规则，不是精确判定。设计上做了两件事控制噪音：
> 1. 阈值偏保守——比如"件数低于中位数 60%"而不是"低于平均值"，中位数对异常值不敏感
> 2. 报告里写明判定依据，比如"卷内共 20 页、脊背 50mm（每毫米仅 0.40 页），而 066 卷 511 页也是 50mm"——**让用户能自己判断这条提醒靠不靠谱**
>
> 我把级别定成"提醒"而不是"错误"，也是这个考虑：可疑不等于错。

### C. 工程实践

**Q9：规则经常变，你怎么让改动成本最低？**

> 四条措施：
> 1. **规则目录化**——所有规则集中在一个数组里，带 id、名称、级别、说明。报告按目录渲染，加一条规则只改数组 + 加检查逻辑
> 2. **通用检查函数化**——24 个列的固定值校验共用一个 `checkUniformColumn`，新增固定列只改列名数组
> 3. **口径文档同步**——`references/rules.md` 写清每条规则的精确判定，改代码必须改文档
> 4. **修正能力**——`--fix-dates` 让"规则变了，历史数据要批量改"变成一条命令
>
> 效果是：最近一次改日期口径（从"各晚一日"改成"倒推工作日链"），前后不到 30 分钟，包括改代码、改文档、改测试、重跑验证。

**Q10：怎么保证检查器和生成器口径一致？**

> 用闭环测试强制约束。生成器的输出直接喂给检查器，要求零错误。
>
> 如果哪天有人改了检查器的规则但没改生成器，这个测试立刻红。
>
> 这是"用测试固化跨模块契约"的典型用法——比写文档约定更可靠，因为它会失败。

**Q11：版本管理为什么用「档号」这种形式？**

> 最初就是普通语义化版本（0.3.0）。后来发现两个问题：
> 1. 同一个版本号在两个技能（检查器/生成器）里，说不清是哪个
> 2. 更新后用户不知道自己在跑哪一版
>
> 所以引入档号前缀：`ALC`（检查器）、`ALB`（生成器）、`LST`（工作台）、`ENG`（引擎）。好处是**任何一处出现档号就能唯一定位**——脚本启动横幅打印档号、`package.json` 里有、README 顶部有、报告里有。
>
> 用户截图给我看问题，我看横幅就知道版本，不用问。

**Q12：内网机器不能上 GitHub，怎么更新？**

> 设计了三条通道，按可用性降级：
> 1. **直连 GitHub**：`git pull` / 下载 release zip
> 2. **镜像源**：jsDelivr CDN（`cdn.jsdelivr.net/gh/...`）、gh-proxy 之类的反代、npm 镜像（`registry.npmmirror.com`）
> 3. **离线更新包**：整包 zip 拷进内网，解压覆盖。因为应用是纯静态的，覆盖即生效，没有数据库迁移、没有依赖安装
>
> 第三条是这个架构的额外红利——**零依赖 + 纯静态 = 离线升级天然可行**。如果当初选了"服务端 + 数据库"，离线更新会变成噩梦。

### D. 业务理解

**Q13：你怎么确认自己理解了归档规范？**

> 靠反复被纠正。记录下来的坑：
> - 以为"编制和立卷同一天"是规则，其实只是样本现象
> - 以为"归档日期 = 检查日期 + 1 天"，实际业务要求"归档写当日"
> - 以为"分类号可以一本台账里混"，实际必须单本一致（模板里的混排是测试数据）
> - 以为"固定值列每行都要填"，实际是每卷首行填一次
>
> 现在我的做法是：**每条规则都要求给一个正例和一个反例**，只给正例的规则不算确认。

**Q14：这个工具帮业务省了多少时间？**

> 坦白说我没有做过严格的工时测量，只有粗糙的估算：人工核对一本 70 件的台账大概 2–3 小时，工具跑完 + 看完报告大概 5 分钟。但**我不建议把这个数字写进简历**，因为没有对照实验，属于主观估计。
>
> 更有说服力的是错误发现率：在一份人工已经检查过两遍的台账上，工具还是找出了"归档日期有两个值"和"8 件缺文件日期"，这两个人工都漏了。

### E. 反思类

**Q15：这个项目最大的技术债是什么？**

> **规则没有单一事实来源。**
>
> 现在同一套规则存在于四个地方：Python CLI、JS 引擎、规则文档、测试用例。改一次要同步四处。虽然我用闭环测试和文档约束降低了风险，但根本问题没解决。
>
> 正确做法是把规则做成**声明式配置**，比如用 JSON 描述"这一列必须唯一""这个字段由表达式推导"，两个实现都读同一份配置。这样规则只写一次。
>
> 没做的原因：规则里有大量非平凡逻辑（日期倒推、档号拆解、可疑卷判定），不是简单的声明式能表达的。做配置化会引入一套 DSL，维护成本可能更高。**这是个典型的"知道有更好的方案但当前不值得"的取舍。**

**Q16：如果重做一次，你会怎么改？**

> 三点：
> 1. **先做数据模型，再写规则**——我一开始是"看到一列写一条检查"，后来发现通用检查能覆盖 24 个列，重构了一次
> 2. **先要反例，再写实现**——所有被推翻的规则，都是因为我只看了正例
> 3. **第一天就建闭环测试**——往返验证是在做了一半才补的，如果早一天做，6.2 那个"数据行没清干净"的 bug 会当场暴露

**Q17：你从这个项目学到什么？**

> 最实在的一条：**做业务工具，领域理解比技术难度重要得多。**
>
> 25 条规则里没有一条技术上难，全部加起来不到 2000 行代码。但这个项目花时间最多的不是写代码，是搞清楚"归档到底怎么算对"。前两版的日期规则全废，原因全是我没问清楚。
>
> 第二条是**假警报的破坏力**。第一版报 137 条错误，用户会直接放弃这个工具。降到 11 条之后，剩下的每一条都被认真看了，其中两条还是真问题。检查工具的产品指标不是"检出数"，是"信噪比"。

## 十、STAR 故事（面试让讲故事时用）

### 故事一：日期规则被推翻三次

- **S** 档案归档要求四个日期（编制/立卷/检查/归档）依次递增，我按样本推出了"编制=立卷、其余各+1 天"的规则并实现
- **T** 上线后被业务方指出口径不对
- **A** 我没有直接改代码，而是先做了一个**工作日倒推的通用函数**，再要求业务方给正例和反例各一个。拿到"归档写当日"这个反例后，发现只有"以归档日为锚倒推"才能同时满足
- **R** 第三次实现稳定至今。同时我把规则从硬编码改成数据驱动的规则目录，后续同类变更成本从半天降到半小时

### 故事二：137 条假警报

- **S** 检查器在真实台账上报 137 个错误，用户直接不想用了
- **T** 需要在不漏真问题的前提下把噪音降下来
- **A** 逐条看报错，发现 90% 是"固定值列存在空值"，根因是台账采用"每卷首行填写"的导出格式。把校验语义改成"非空值必须唯一 + 整列全空才算错"
- **R** 从 137 条降到 11 条。降噪之后，原本被淹没的"归档日期有两个值"（`20260803` vs `20260930`）浮了出来——这条是真错误，人工检查两遍都没发现

### 故事三：没人相信工具算对了

- **S** 工具跑出来"0 错误"，但同事不信，觉得是"什么都没检查"
- **T** 需要一个能证明"它真的在检查"的方法
- **A** 做了三层验证：① 往正确数据里注入 3 处已知错误，看能否检出；② 从真台账提取 8 项要素重新生成，逐字段比对（26 件 × 25 字段，0 差异）；③ 生成器输出必须通过检查器，形成闭环
- **R** 现在"0 错误"是有说服力的结论，因为反例测试证明规则不是空壳
